# 두 PC에서 P2P 대전 인수검사

**현재 상태는 실기 측정 전이다.** 3차 요구사항 8~10쪽의 대상은 같은 LAN에 연결한 서로 다른 두 PC다. 입력자가 누른 키부터 상대 모니터에 블록이 표시될 때까지 **200ms 이하**인지 양방향으로 확인한다. 기존 Mac 한 대의 두 창 측정값과 자동 장애 검사는 [브랜치 2 검증 기록](p2p-network-verification.md)에 있다.

## 준비

1. 호스트 A와 클라이언트 B에 같은 제출 후보 소스로 만든 각 OS용 패키지를 준비한다. 검사 일시, 커밋 SHA, 각 ZIP의 파일명·SHA-256, 두 기기의 OS·기종·화면 주사율, 유선 또는 Wi-Fi 연결 방식을 기록한다.
2. 두 PC에서 각각 시작 메뉴의 `SCORE`를 열고 `All`·`Classic`·`Item` 순위를 캡처한다. 저장 기록이 전혀 없다면 먼저 1인 게임 한 판을 끝내 이름과 점수를 저장한 뒤 캡처한다. 각 PC에서 패키지의 점수 파일(사용자 홈 아래 `.seoultech-tetris/tetris_score.txt`)의 SHA-256도 기록한다. 순위 화면에는 상위 10명만 보인다.
3. 두 PC를 같은 LAN에 연결한다. 양쪽에서 게임을 열고 `P2P BATTLE`을 선택한다. A는 `HOST GAME`을 누르고 공통 LAN의 IP를 알려 준다. B는 IP만 입력하고 `JOIN GAME`을 누른다. 기본 TCP 포트는 30000이다.
4. 아래 순서대로 검사한다. 각 결과에 **모드·방향·기대 동작·관찰 결과·영상 파일과 구간**을 남긴다. 통과 여부는 실제로 본 항목에만 표시한다.

## 경기 확인

| 순서 | 두 사람이 할 일 | 화면에서 확인할 것 |
|---|---|---|
| 1. 준비와 시작 | A가 Classic을 선택하고 B만 `START`를 누른다. 이어서 A도 누른다. | 첫 번째 입력 후 두 화면 모두 로비에 머문다. 두 번째 입력 후 양쪽에 내 보드와 상대 보드가 나타난다. |
| 2. 이동과 공격 | A와 B가 번갈아 좌우 이동한다. 한 사람은 일반 블록 하나로 2줄 이상을 완성하고, 상대는 예고를 확인한 뒤 현재 블록을 고정한다. 역할을 바꿔 반복한다. | 입력한 사람의 왼쪽 보드와 상대 PC의 오른쪽 보드에서 같은 블록이 움직인다. 공격 예고에 마지막 블록 자리가 빈 모양이 보이고, 수신자의 블록 고정 후 그 모양대로 바닥에 회색 공격 줄이 한 번 올라와 직접 쌓은 블록과 구별된다. |
| 3. 승패와 재대전 | Classic에서 한쪽이 더 쌓을 수 없도록 한다. 같은 연결에서 Item을 선택해 재시작한다. Item에서는 누적 10줄을 지워 아이템을 받고 사용한 뒤 경기 종료까지 진행한다. | 양쪽 결과 화면에 각각 `YOU WIN`과 `YOU LOSE`가 뜨고 내 점수와 상대 점수가 서로 맞는다. 한쪽이 먼저 `CONTINUE`를 눌러도 결과가 유지된다. 다른 쪽도 확인한 뒤 로비에서 다시 두 사람이 준비해야 새 판이 시작되며 점수와 공격 예고가 초기화된다. 아이템의 효과와 점수가 양쪽에 일치한다. |
| 4. 시간제한 | 같은 연결에서 Time Limit을 시작한다. 한쪽만 점수를 올린 뒤 양쪽 모두 보드 상단에 닿지 않은 채 제한시간을 끝낸다. | 양쪽 타이머와 점수가 일치하고, 시간이 끝나면 높은 점수 쪽이 승리한다. 양쪽 로비에서 다시 경기 시작이 가능하다. 세 모드 모두 경기 종료 후 이름 입력 창이 뜨지 않는다. |

## 키 입력부터 상대 화면까지 측정

지연을 인위적으로 추가하기 **전**에 측정한다. 팀의 표본 계획은 Classic·Item·Time Limit 각각 방향별 5회, 총 30회다. PDF가 지정한 수치는 200ms이며 표본 수는 팀이 정했다.

1. 카메라 한 대에 **입력하는 키보드와 상대 PC의 오른쪽 보드**를 함께 담는다. 원본의 실제 촬영 속도를 확인한다(권장 120fps 이상). 방향을 바꿀 때 카메라도 옮긴다. 이렇게 하면 두 PC의 시계를 맞출 필요가 없다.
2. 블록이 벽에서 떨어진 상태에서 저장된 좌·우 키를 번갈아 한 번씩 누른다. 한 칸 이동이 보인 다음에 다음 키를 누르고, 원본 영상과 입력 순서를 보관한다.
3. 시도마다 키가 내려가기 **직전의 마지막 정지 프레임**을 `K`, 상대 화면에서 같은 블록이 목표 열에 보이는 **첫 프레임**을 `S`로 기록한다. 한 프레임 안에서 발생 시점을 특정할 수 없으므로 `K`의 시작부터 `S`의 끝까지를 보수적인 상한으로 잡는다.
4. 고정 촬영 속도 `F`에서 **상한(ms) = (S − K + 1) × 1000 / F**다. 예를 들어 120fps에서 K=100, S=122면 상한은 191.67ms다. 가변 프레임 영상은 원본 촬영 시각으로 `S 다음 프레임의 시작 − K 프레임의 시작`을 사용한다. 슬로모션 재생 속도만 알거나 손·블록이 가려진 시도는 사유를 남기고 다시 촬영한다.
5. 세 모드 × 두 방향의 여섯 조합별로 유효 표본 수와 최댓값을 기록한다. 각 조합에 유효 입력이 5회 이상이고 모든 유효 입력의 반올림 전 상한이 200ms 이하일 때 정상 LAN 검사를 통과로 기록한다. 유효한 상한이 200ms를 넘으면 해당 회차는 충족 미확인으로 남긴다. 재측정은 별도 회차로 기록하고 최초 영상과 수치를 함께 보존한다. TCP 왕복시간(RTT)은 네트워크 상태 참고값이다.

시도별 원자료는 아래 열로 저장한다. 한 행이 키 입력 한 번에 해당한다.

```csv
session_id,mode,direction,trial,key,video_file,capture_fps,K,S,K_start_ms,S_end_ms,upper_bound_ms,status,note
```

## 느린 연결 · 단절 · 재접속

아래의 999ms와 10초는 게임의 [통신 판정 기준](p2p-network-gui-specification.md)이다. 정상 LAN 200ms 결과와 별도로 기록한다.

| 상황 | 실행과 기대 결과 |
|---|---|
| 느리지만 패킷이 도착함 | 팀 시험 기기 한 대의 네트워크 지연 도구에서 송신·수신에 각각 550ms 지연, 손실 0%를 설정한다. 통신이 안정된 뒤 두 화면의 `slow connection` 경고와 실제 이동 반영을 확인한다. 지연 설정을 해제하면 같은 경기에서 경고가 사라져야 한다. |
| 잠깐 응답이 멎음 | 시험 기기의 지연 도구로 게임 트래픽을 2~3초간 차단했다가 복원한다. 소켓이 유지됐을 때 `waiting for peer`와 경기 정지, 복원 후 같은 판의 재개를 기록한다. 시험 기기에서 설정하고 매 시도 뒤 원복한다. |
| 연결이 끊김 | 같은 방식으로 10초 넘게 수신을 차단한다. 오류 안내와 최초 P2P 접속 화면 복귀를 확인한다. 운영체제가 먼저 소켓을 닫으면 즉시 단절 사례로 기록하고 장시간 무응답과 구분한다. |
| 다시 접속 | 네트워크를 정상으로 돌린 후 A가 다시 방을 연다. B의 앱을 다시 열어 마지막 성공 IP가 표시되는지 확인한 후 그 주소로 접속한다. 두 사람이 모두 준비해 다시 게임을 조작할 수 있어야 한다. |

지연 도구를 쓸 수 없는 환경에서는 확인한 상황만 기록한다. 같은 PC에서 실행한 [지속 지연 검사](../src/test/java/seoultech/se/tetris/network/P2PContinuousLatencyTest.java)와 [한 방향 통신 중단 검사](../src/test/java/seoultech/se/tetris/network/P2PDirectionalDelayTest.java)는 팀의 실기 기록과 함께 참고할 수 있다.

모든 경기와 재접속 검사가 끝나면 양쪽 앱을 종료했다가 다시 열어 `SCORE`를 확인한다. 준비 단계의 세 필터 화면과 이름·점수·순서를 대조하고 전후 캡처를 같은 기기별로 보관한다. 각 PC의 점수 파일 SHA-256이 그 PC에서 시작 전에 기록한 값과 같아야 한다.
